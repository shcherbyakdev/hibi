# Recurring Steps Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Steps that come back on their own, every day or on chosen weekdays, so a goal's daily habit doesn't have to be retyped each morning.

**Architecture:** A synced `routines` table holds the rule (title, priority, goal, weekdays). Each day the client makes that day's copy: an ordinary `items` row with `routine_id`, planned for today. The copy's id is derived from (routine, date), so two devices make the same row. Its `updated_at` is a fixed old stamp, so any real edit (tick, delete, rename) always wins last-write-wins on both client and server. No server cron; works offline.

**Tech Stack:** Next 16, React 19, Drizzle + Supabase (RLS, Realtime), Dexie, Vitest. The pipline-app recurrence feature is a different domain (certificate re-arming); only its discipline carries over: a pure core with `now` injected.

**Spec:** the "Design" section below. The user skipped the questions, so these are my calls.

## Design

- **Routine** = `title`, `priority`, `goal_id?`, `days` (weekday bitmask: bit 0 = Sunday … bit 6 = Saturday, 127 = every day; check 1–127). Delete is soft, like every synced table. There is no pause; delete it, and the past copies stay.
- **Copies:** only **today's** copy is made (on app open, at midnight rollover, and when a routine is created or edited), and only if today's weekday is in `days`. There is no backfill for missed days and no future copies in the week or month views.
  - **Id:** UUID v5-style, SHA-1 of `${routine_id}:${date}`.
  - **Stamp:** `updated_at = "2000-01-01T00:00:00.000Z"`.
  - **Exists check:** before making a copy, check whether any local item already has (`routine_id`, `plan_date = today`), deleted or not. A deleted copy means the user skipped today, so it stays skipped.
  - **Wait for sync:** copies are made only after the device's first sync cycle finishes, or when it's offline. That way a device that just opened doesn't race the pull of a copy another device already ticked.
- **Missed days don't pile up:** open routine copies are left out of the Overdue group. Yesterday's unticked copy stays on yesterday, as an empty grid cell.
- **Editing a routine** changes copies from the next one on. Today's existing copy is left as it is.
- **Where you set it up:**
  1. **Goal page:** a "Routines" section above Open. Each routine shows its title, a day picker (7 toggles, ordered by the week-start setting) and Delete. "Add a routine" creates one with `days = 127` and the goal linked, and today's copy appears straight away.
  2. **Task sheet:** a "Repeat" field.
     - On a plain task, picking days turns it into a routine: it creates the routine from the task's title, priority and goal, and sets `task.routine_id`, so the task counts as today's copy.
     - On a copy, the field edits its routine's days. "Never" deletes the routine; the copies stay.
- **Not now:** monthly or interval rules ("every 2 days", "pay rent on the 1st"), future copies in the week or month views, pause, and backfilling missed days. Add them if real use asks.

## Global Constraints

- Follow `AGENTS.md`. Copy the patterns from the goals feature (`features/goals/*`, migrations `0007`/`0008`).
- Dates are local calendar dates: `toISODate` and `fromISODate` from `features/planner/periods.ts`. The weekday comes from `fromISODate(date).getDay()`.
- No new dependencies. Hashing uses `crypto.subtle`, which is available in browsers on localhost or https, and in Node 24.
- The new table gets the full sync treatment from `0008_goals_rls.sql`: owner FK, `sync_stamp`, `REVOKE ALL` then CRUD for authenticated, owner RLS, Realtime. It also gets the `ponytail:` FK note for `goal_id`.
- `SYNCED_TABLES` order: `"boards", "board_columns", "goals", "routines", "items", "time_entries"`.
- `npm run verify` must pass at every commit. Production migrations are run by hand (see the README) before the client deploy goes live.

## Review Focus

1. **A copy ticked on device A, then generated by device B**, which was offline and hasn't pulled: after sync, the task stays done. Pinned in the Task 2 engine test (c).
2. **A copy deleted today:** it must not come back on reload. Pinned in the Task 2 `ensureToday` test (a deleted copy counts as existing).
3. **A task turned into a routine through the sheet:** it must not get a second copy today. Pinned in the Task 2 test (an existing `routine_id` + date match skips).
4. **Rollover at midnight with the tab open:** the next day's copy appears. `useToday` already ticks every minute; the runner reruns when today changes. Covered by the Task 5 manual check.
5. **Week start = Sunday:** the day picker order follows the setting, while the bit for each day stays the same. Pinned in the Task 1 `dayOrder` test.

### Task 1: Rule model

**Files:**
- Create: `src/features/routines/model.ts`
- Test: `src/features/routines/model.test.ts`

**Interfaces:**
- Produces:
  - `EVERY_DAY = 127`
  - `dayBit(date: string): number`, which returns `1 << fromISODate(date).getDay()`
  - `isDue(days: number, date: string): boolean`
  - `toggleDay(days: number, weekday: number): number`. It never returns 0: clearing the last day keeps it set.
  - `dayOrder(weekStart: 0 | 1): number[]`, the weekday indices in display order (`[1,2,3,4,5,6,0]` or `[0..6]`).
  - `DAY_LETTERS = ["S","M","T","W","T","F","S"]`, indexed by weekday.
  - `occurrenceId(routineId: string, date: string): Promise<string>`. This is SHA-1 → UUID with the version nibble set to 5 and the variant to `10xx`.
  - `GENERATED_STAMP = "2000-01-01T00:00:00.000Z"`

- [ ] **Step 1: Write the failing tests.**
  - `isDue(127, any)` is true. `isDue(dayBit("2026-11-14") /* Sat */, "2026-11-14")` is true, and false for `"2026-11-15"`.
  - Weekdays-only `0b0111110`: true on Mon 2026-11-09, false on Sun 2026-11-08.
  - `toggleDay(127, 0) === 126`. `toggleDay(1, 0) === 1`, because it never empties.
  - `dayOrder(1)` equals `[1,2,3,4,5,6,0]`. `dayOrder(0)` equals `[0,1,2,3,4,5,6]`.
  - `occurrenceId` is the same for the same inputs and different for another date. It matches `/^[0-9a-f]{8}-[0-9a-f]{4}-5[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/`.
  - Under `TZ=Asia/Tokyo`, `isDue(dayBit("2026-11-14"), "2026-11-14")` is still true. The day comes from local date parts, never from UTC.
